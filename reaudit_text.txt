Independent Re-Audit of the Major Revision
Riemann Zeta Lean 4 formalization, paper, repository, CI, and release package
Overall verdict: the revision is a major improvement, but it is not publication-ready. The current public release makes verification claims contradicted by its own CI, misstates the toolchain, miscounts the audit, overstates the Hardy Z formalization, and contains multiple incorrect citations.
This report distinguishes source inspection, external verification, and inference. It does not claim a successful local Lean build.
Executive verdict
The revision repaired many of the worst defects in version 5. The “universal zero locator” rhetoric has been removed; positive indices are now enforced with ℕ+; the fourfold completed-zeta theorem now actually returns all four symmetry evaluations; a Hardy Z-style function is defined; the pole at s = 1 is disclosed; and the workflow was moved to the repository-level GitHub Actions directory. Those are real corrections, not cosmetic changes.
However, the release package still fails its own stated standard. The paper says “0 errors, 0 warnings” and “stable v4.30.0.” The public Riemann Zeta workflow is red with two errors and one warning, and the checked-in toolchain is v4.30.0-rc2. The paper says 18 audited declarations, while Audit.lean prints 19. The paper calls hardyZ the classical Hardy Z-function but never proves it is real-valued, which is the defining analytic feature used for sign changes. Three references have incorrect journal or page data. These are publication blockers because they affect verifiability, mathematical scope, and bibliographic reliability.
Immediate publication decision
Do not describe the current main branch as a verified version 1.0.0 release. Repair the CI, align the toolchain and declaration count, correct the references and completed-zeta definition, and either prove Hardy Z is real-valued or rename it as a complex-valued Hardy-type function.
What the major revision genuinely fixed
1. Inflated “universal zero locator” claims removed
The revised paper and source use direct names such as crossNormProduct_eq_zero_of_left, crossNormProduct_eq_zero_of_right, and crossNormProduct_eq_zero_iff. This accurately describes multiplication and norm-zero facts instead of presenting them as a zeta-zero location method.
2. Positive-index domain enforced
dirichletPoly now takes coefficients indexed by ℕ+ and a Finset ℕ+. The previous n = 0 complex-power defect is therefore removed at the type level.
3. Fourfold theorem now matches its name
completedRiemannZeta_fourfold_zero_orbit returns conjunctions for σ+it, 1-σ-it, σ-it, and 1-σ+it. Version 5 only proved one reflected partner.
4. Hardy Z-style object now exists
The repository now defines riemannSiegelTheta and hardyZ and proves norm equality and zero equivalence. This is much better than applying “HardyZ” labels to completed-zeta symmetry alone.
5. Pole disclosure added
The paper and Nonvanishing.lean now distinguish the classical pole at s = 1 from Mathlib’s totalized value.
6. Repository publication files improved
The subproject now includes a license, citation metadata, a revised README, a dedicated audit module, and a root-level Riemann-specific workflow.
7. Scope limitations stated
The README and paper explicitly say that the finite identities are not Guth-Maynard zero-density estimates and that symmetry does not prove non-existence of off-line zeros.
1. [BLOCKER] The public Riemann Zeta CI fails
The dedicated workflow run for commit 9295e56 has status Failure. GitHub reports “lake check-lint failed: could not find a lint driver,” exit code 1, and a Node.js deprecation warning caused by actions/checkout@v4. A paper cannot honestly claim a clean, warning-free public verification while its project-specific verification badge would be red.
Repair: Set lint: false unless a lint driver is deliberately configured, update actions/checkout to v5 or newer, rerun the workflow, and cite the successful run or commit in the release notes.
2. [BLOCKER] The repository-wide Lean workflow also fails
The generic Lean Action CI run for the same commit has status Failure and the annotation “lake build failed.” It runs at repository root without selecting the Riemann Zeta package, even though this is a multi-project repository. This second red workflow makes the release look broadly broken.
Repair: Remove the generic workflow, convert it into a proper monorepo matrix, or apply package directories and path filters. Remove GitHub Pages permissions unless the job actually publishes documentation.
3. [BLOCKER] “0 errors, 0 warnings” is contradicted by public evidence
The abstract, section 6, and README claim clean verification. GitHub currently records two errors and one warning for the Riemann-specific workflow and two errors for the generic workflow. A private local build could still have succeeded, but no committed log or green CI run substantiates the published wording.
Repair: Replace the claim with a dated, commit-specific statement only after green CI. Distinguish Lean compiler diagnostics from workflow warnings. Commit an audit artifact or upload it as a workflow artifact.
4. [BLOCKER] Stable Lean 4.30.0 is falsely reported
The paper and README repeatedly state v4.30.0 stable. lean-toolchain pins leanprover/lean4:v4.30.0-rc2, and lake-manifest.json pins Mathlib and inherited packages to v4.30.0-rc2. The stable Lean v4.30.0 release exists separately.
Repair: Either change every document to “v4.30.0-rc2” or upgrade lean-toolchain to v4.30.0, run lake update, rebuild, and commit the regenerated manifest.
5. [BLOCKER] The audit count is internally inconsistent
The paper and README say 18 core declarations. Audit.lean contains 19 #print axioms commands. The paper table lists 18 declarations but omits riemannZeta_ne_zero_totalized, while Audit.lean includes that theorem and omits riemannZeta_ne_zero_of_re_ge_one_of_ne_one. The published mapping and the actual audit are not the same set.
Repair: Define one canonical declaration list. Make the table, README, Audit.lean, abstract, and CI output agree exactly. State whether helper wrappers are counted.
6. [BLOCKER] The completed-zeta definition is stated without its pole exceptions
The paper says Λ(s) = π^(-s/2) Γ(s/2) ζ(s) as a global definition. Mathlib documents that the identity has a correction at s = 0 and that Λ is mathematically undefined at s = 0 and s = 1, although the Lean construction assigns values there. The manuscript discloses only the pole of ζ at s = 1.
Repair: State the formula away from s = 0 and s = 1, then describe Mathlib’s totalized assigned values. Add a completed-zeta pole disclosure alongside the zeta pole disclosure.
7. [BLOCKER] The object called “classical Hardy Z-function” is not proved real-valued
hardyZ is defined with codomain ℂ. The only proved results are preservation of norm and zeros under multiplication by a nonzero unit complex factor. The classical Hardy Z-function is real-valued for real t, and that property is what supports sign-change arguments. The repository does not prove (hardyZ t).im = 0, star (hardyZ t) = hardyZ t, or an equivalent real-valued formulation.
Repair: Until real-valuedness is proved, call this a complex-valued Hardy-type normalization. For the classical claim, formalize the phase relation needed to prove realness and preferably expose a real-valued function ℝ → ℝ.
8. [BLOCKER] The bibliography contains three factual errors
Guth-Maynard is pages 623-675, not 311-385. Loeffler-Stoll appeared in Annals of Formalized Mathematics, not Journal of Automated Reasoning. Ingham’s article is pages 201-202, not 201-219. These are not stylistic disagreements; they are incorrect bibliographic data.
Repair: Replace all three entries with verified metadata and add DOI values where available.
9. [MAJOR] The paper overstates the Hardy Z result as “foundational properties” of the classical function
Norm preservation and zero preservation follow from the phase factor having norm one and being nonzero. Those statements are correct but elementary. Without realness, continuity, parity, theta identities, or sign-change properties, the formalization does not yet capture the classical computational role of Hardy Z.
Repair: Narrow the claim to “a Hardy Z-style normalization with norm and zero equivalence” or add the missing classical theorems.
10. [MAJOR] The Riemann-Siegel theta identification is insufficiently justified
riemannSiegelTheta is defined using the imaginary part of Complex.log (Gamma z), which is a principal-argument representative. DLMF uses the principal phase but explicitly notes that theta is chosen to make Z(t) real. The repository proves neither that its branch convention yields that realness nor that it agrees with a continuous Riemann-Siegel theta across the intended domain.
Repair: Add a theorem relating this definition to the functional-equation phase and prove realness. Document branch conventions and any interval or modular ambiguity.
11. [MAJOR] The fourfold “orbit” need not contain four distinct points
At t = 0, conjugate points coincide. At σ = 1/2, reflection points coincide. The theorem correctly returns four evaluations, but “all four orbit points” can be read as four distinct zeros.
Repair: Use “four symmetry evaluations” or “fourfold symmetry tuple,” and state that points may coincide on symmetry loci.
12. [MAJOR] The fourfold theorem is mostly a coordinate wrapper around Mathlib results
The proof composes Mathlib’s completedRiemannZeta_one_sub and completedRiemannZeta_conj with simple coordinate identities. This is useful packaging, but it is not a new analytic result about zeta zeros.
Repair: State the contribution as a reusable coordinate theorem derived from existing Mathlib symmetries.
13. [MAJOR] “100% machine-checked infrastructure” remains too broad
The repository checks selected finite identities and wrappers around Mathlib theorems. It does not formalize the Guth-Maynard analytic machinery, zero-density estimates, Hardy Z realness, or a general Dirichlet-polynomial analytic framework. The phrase suggests greater coverage than the source supplies.
Repair: Use “a small machine-checked library of finite identities and symmetry wrappers.”
14. [MAJOR] The theorem described as a bilinear real-part bound is not formalized as a bilinear map
realPart_abs_le_crossNormProduct applies |Re z| ≤ ‖z‖ and norm multiplicativity to a product of two complex evaluations. No bilinear form or sesquilinear structure is defined. “Bilinear” is suggestive but technically unsupported.
Repair: Rename it “real-part bound for the evaluation product” unless an actual bilinear map is introduced.
15. [MAJOR] The module names still preserve discarded concepts
DirichletDensity contains no density or counting theorem. AsymmetricEnergy contains a product of norms, not an energy theory. PhaseWinding contains no phase or winding invariant. The revised paper is more honest than the filenames.
Repair: Rename to FiniteDirichletPolynomial.lean, CrossNormProduct.lean, and CompletedZetaSymmetry.lean.
16. [MAJOR] The paper presents inherited Mathlib nonvanishing as if it were a project theorem
riemannZeta_ne_zero_of_re_ge_one_of_ne_one immediately calls Mathlib’s riemannZeta_ne_zero_of_one_le_re. The one-line theorem is a coordinate specialization. The heavy analytic proof is entirely in Mathlib.
Repair: Label these declarations as wrappers or corollaries of Mathlib’s nonvanishing theorem and cite the Mathlib module directly.
17. [MAJOR] The first nonvanishing wrapper has an unused hypothesis
riemannZeta_ne_zero_of_re_ge_one_of_ne_one accepts hne : s ≠ 1, but its proof does not use hne because the imported Mathlib theorem also covers the totalized value at s = 1. The statement is classically sensible, but the proof object does not depend on its classical-domain condition.
Repair: Either keep it as an explicitly documented classical-domain wrapper and acknowledge the unused premise, or prove a theorem about a partial/meromorphic formulation where the premise matters.
18. [MAJOR] The paper omits a direct account of imported theorem dependencies
The completed-zeta functional equation, conjugation symmetry, and half-plane nonvanishing are already in Mathlib. The paper’s mapping table lists only project declarations and can leave readers with the impression that the project established the underlying analytic theorems.
Repair: Add a “Mathlib dependencies” column or a separate dependency table naming completedRiemannZeta_one_sub, completedRiemannZeta_conj, and riemannZeta_ne_zero_of_one_le_re.
19. [MODERATE] The positive-index repair is correct but the “singularity” wording is loose
Using ℕ+ eliminates the ambiguous or undesirable n = 0 complex-power case. Calling that case a “complex power singularity” is informal because Lean’s functions are totalized and may assign values rather than become undefined.
Repair: Say that positive indexing removes the n = 0 branch and aligns the formal definition with classical Dirichlet polynomials.
20. [MODERATE] threshold_conj_line_iff is mathematically valid but analytically thin
The threshold theorem is merely substitution of an equality of norms. It quantifies over every real V, including negative thresholds, and contains no counting, measure, or density content.
Repair: Describe it as a threshold predicate equivalence, not a large-value estimate.
21. [MODERATE] dirichletPoly_zero_conj is only stated in one direction
Conjugation is involutive, so an equivalence is available. The current one-way theorem is correct but weaker than the surrounding duality narrative suggests.
Repair: Add an iff theorem or explain why the one-way corollary is the only API needed.
22. [MODERATE] The cross-norm zero characterization is tautological
The result follows from mul_eq_zero and norm_eq_zero. It is a useful API lemma, but it does not detect zeros computationally or analytically beyond inspecting the two factors.
Repair: Describe it as a zero-factor characterization and avoid “detection” language unless an algorithm is supplied.
23. [MODERATE] The first conjunct of the fourfold theorem simply repeats the assumption
The theorem returns the original zero as part of a four-item conjunction. This matches a display-friendly tuple but adds no proof content.
Repair: Consider returning the three generated symmetry consequences, or define the orbit as a finite set and state vanishing on every member.
24. [MODERATE] Hardy Z parity and critical-line symmetry are not connected to hardyZ
HardyZ.lean proves completed-zeta symmetry and separately defines hardyZ, but there is no theorem such as hardyZ (-t) = hardyZ t. This further limits the claim to classical Hardy Z properties.
Repair: After resolving the phase convention, add evenness and a real-valued theorem.
25. [MODERATE] There are no examples or executable sanity checks
The package contains abstract declarations only. Small #eval examples are not appropriate for noncomputable zeta values, but theorem-level examples or test modules could demonstrate API use.
Repair: Add a Tests or Examples namespace with finite Dirichlet-polynomial special cases and symmetry applications.
26. [MODERATE] The manuscript uses “revolutionary” for Guth-Maynard
The source paper is important, but “revolutionary” is promotional and unnecessary in a formalization report, especially when the project does not mechanize that work.
Repair: Use “recent” or “substantial.”
27. [MAJOR] #print axioms is not a pass/fail audit by itself
#print axioms prints dependencies. It does not automatically fail the build when sorryAx appears. The workflow does not capture and scan this output. Calling the mechanism “automated audit” overstates what is enforced.
Repair: Run Audit.lean in CI, tee the output to an artifact, grep for sorryAx, and fail the job when found.
28. [MAJOR] Mathlib.Util.PrintSorries is imported but unused
Audit.lean imports PrintSorries but invokes only #print axioms. The import creates the appearance of a stronger no-sorry check without using it.
Repair: Use the intended command or remove the import. Prefer a CI check that fails deterministically.

Repair: Remove the Audit import from RiemannZeta.lean. Run it as a separate CI target or test file.

Replacement wording for the most problematic passages
Replacement abstract
We present a Lean 4 library of finite positive-index Dirichlet-polynomial conjugation identities and coordinate corollaries of Mathlib’s completed Riemann zeta symmetries. The library defines finite Dirichlet polynomials over ℕ+, proves conjugation and norm invariance, packages a product-of-norms API with elementary factor-swap and zero-factor lemmas, and derives the four standard symmetry evaluations associated with a zero of the completed zeta function. We also define a complex-valued Hardy-type normalization on the critical line and prove that it has the same norm and zeros as the Riemann zeta function there. These results do not formalize zero-density estimates, do not rule out off-line zeros, and do not yet establish that the Hardy-type normalization is real-valued. Verification details are tied to the tagged repository release and its successful CI audit.
Replacement completed-zeta paragraph
Away from s = 0 and s = 1, Mathlib’s completed Riemann zeta function agrees with the classical expression Λ(s) = π^(-s/2) Γ(s/2) ζ(s), subject to Mathlib’s documented normalization at the exceptional points. Mathlib’s totalized construction assigns values at s = 0 and s = 1 even though the classical meromorphic function has poles there.
Replacement Hardy Z paragraph before real-valuedness is proved
For real t, define the complex-valued Hardy-type normalization H(t) = exp(i θ(t)) ζ(1/2 + it). We prove ‖H(t)‖ = ‖ζ(1/2 + it)‖ and H(t) = 0 if and only if ζ(1/2 + it) = 0. The present development does not yet prove that H(t) is real-valued or identify it fully with the classical real Hardy Z-function.
